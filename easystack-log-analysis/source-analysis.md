# Source Analysis

## Scope 范围

当同时满足以下条件时使用本流程: 已发现 kernel、驱动、系统调用、动态库或 RPM/DEB
软件包相关直接信号; 已完成对应日志和配置的定向检索; 现有证据只能确认直接失败不能
解释触发机制; 且源码分析有明确目标, 例如函数、模块、系统调用或 package 文件。只有
通用 ERROR、没有 kernel/package 信号或现有证据已经闭合根因时, 不要 clone 源码。源码
调研用于补强 bundle 证据, 不能把社区源码默认当作目标环境实际运行代码。

## Workflow 工作流

### Step 1: 从 bundle 提取版本事实

先在已解压的 `ecs.*` 目录中定向查找并保留:

1. OS 发行版、版本、架构和 kernel release.
2. 目标 RPM/DEB 软件包的完整版本、release、架构和安装来源.
3. 相关模块、驱动、动态库、编译器 ABI 或发行版补丁信息.
4. 容器镜像 digest、用户态软件包版本和宿主机与容器的边界.

优先使用 bundle 中的 package manifest、命令输出和启动信息。只有实际命中 bundle 的
内容才能作为环境版本事实; 找不到时将缺口写入报告的 `未确认项与限制`。

### Step 2: 建立临时源码目录

源码只能 clone 到可复用的临时目录, 例如 `/tmp` 下已约定的源码目录; 不得使用 `mktemp`
创建一次性源码目录。复用已有目录前
必须检查 remote、当前 commit、branch/tag、dirty state、补丁状态和当前用途。任何一项
无法确认时, 不覆盖该目录, 改用新的临时子目录。后续分析仍需要使用时保留该目录, 不要求
每次任务结束立即删除。不得写入
bundle、当前 skill 仓库或共享目录。优先使用上游官方仓库或发行版维护的源码仓库;
网络、权限或仓库不可访问时, 记录未执行项, 不用未经验证的本地缓存冒充源码来源。

### Step 3: 对齐版本和构建差异

按以下优先级选择源码状态:

1. 精确匹配 bundle 中发行版 source package 的版本和 release.
2. 使用发行版源码仓库中的对应 tag、分支或 patch queue.
3. 只有无法取得发行版源码时, 才使用社区上游对应 release/tag, 并明确记录发行版补丁
   和构建差异未知。

切换源码后记录仓库地址、tag 或分支、完整 commit、子模块状态、应用的补丁和本地构建
   选项。不要停留在默认分支, 不要把当前最新源码的行为直接映射到 bundle 中的旧环境。

clone 或 checkout 失败时最多记录一次失败原因。存在已验证的本地源码目录时转入版本校验;
否则停止源码分支, 继续使用已有日志和配置证据, 并将源码缺口写入`未确认项与限制`。

### Step 4: 进行只读分析

围绕 bundle 已确认的错误时间、调用栈、系统调用、模块、函数或软件包文件定向检索
源码。保存源码路径、函数或符号、行号、版本状态和它与 bundle 日志的对应关系。源码
只能解释已观察到的现象; 没有日志、配置、core dump、trace 或受控复现支持时, 不把
源码中的可能路径写成已确认根因。

### Step 5: 回填调查证据

报告中区分以下内容:

1. bundle 直接证据: 日志、命令输出、package manifest、配置或操作记录.
2. 对齐源码证据: 仓库、版本、commit、补丁状态、源码路径和相关函数.
3. 推断边界: 源码解释了哪一段传导链, 哪些构建差异或运行时条件仍未验证.

若源码版本无法精确对齐, 只能写为辅助分析或补证建议, 不得单独作为根因结论。分析
完成且不再需要时再清理临时源码目录; 若因后续分析保留, 记录目录用途和版本状态。

## Safety 门禁

- 只读 clone、checkout、grep、构建系统静态读取和源码分析默认允许在本地临时目录执行.
- 需要下载依赖、编译内核或软件包、运行测试、访问私有仓库或修改远程环境时, 先说明
  影响、凭据和清理方式, 并按当前任务的授权门禁单独确认.
- 不复制、提交或输出 token、私有 URL、客户数据、未脱敏日志和内部补丁内容.
- 不因源码分析结果直接执行 restart、升级、降级或替换软件包.

## Execution Feedback 执行反馈

若版本无法对齐、社区仓库不可访问、临时目录不可复用或因权限导致流程绕行, 任务结束
时报告触发位置、实际影响、临时处理和建议优化; 没有实际问题时不输出空反馈。
