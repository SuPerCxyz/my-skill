# easystack-ui-test patterns 层重构设计

## 背景

`easystack-ui-test` 当前已经形成了较完整的 UI 自动化知识库和
操作示例，但 `patterns/` 目录作为“原子操作库”仍存在以下问题:

- `SKILL.md` 声明统一使用 MCP Playwright 和
  `browser_run_code_unsafe`，但基础文档中仍混用 Python Playwright
  模板与 JS 片段
- `quick-reference` 以函数名索引能力，但对应文档实际没有稳定的
  函数契约，更多是匿名代码块集合
- URL、登录方式、等待方式、返回值格式没有统一规范
- 多处存在环境地址、用户名、密码硬编码，导致文档与具体环境强绑定

这些问题会直接降低 skill 的可复用性、迁移性和维护效率。

## 本轮目标

本轮只重构 `patterns` 核心层，建立后续可复制的统一契约。

范围限定为:

- `patterns/login.md`
- `patterns/instance-ops.md`
- `patterns/quick-reference.md`

本轮不做的事情:

- 不重写 `patterns/volume-ops.md`
- 不重写 `patterns/network-ops.md`
- 不改各资源页面知识文档的细节内容
- 不引入新的执行脚本、测试框架或真实运行验证

## 设计原则

### 1. 文档角色单一

- `login.md` 只负责公共前置能力
- `instance-ops.md` 只负责实例域操作契约和样板
- `quick-reference.md` 只负责能力索引，不承载实现细节

### 2. 执行语义统一

所有示例和约定统一以 MCP Playwright 的
`browser_run_code_unsafe` 为目标执行模型，不再提供 Python
Playwright 模板。

### 3. 环境解耦

文档不再硬编码真实平台地址、用户名、密码。所有操作统一假设:

- 环境配置来自 `/tmp/easystack-env.json`
- 运行前先读取配置
- 用例参数优先级高于环境默认值

### 4. 返回值结构化

操作结果不再使用随意字符串，统一定义结果结构，便于后续测试编排、
错误处理和结果持久化。

## 文档结构设计

## `patterns/login.md`

### 职责

定义所有原子操作共享的前置能力:

- 环境配置读取约定
- 登录流程
- 会话复用策略
- 通用等待策略
- 通知和遮挡处理
- 页面到达验证

### 目标结构

建议按以下章节组织:

1. 适用范围
2. 环境配置来源
3. 登录契约
4. 会话复用契约
5. 通用辅助动作
6. 返回值约定
7. 标准示例

### 关键约定

- 所有操作先尝试复用已有会话，再决定是否登录
- 登录成功判定必须基于 URL 或页面关键元素，不以点击按钮代替成功
- 页面等待以“目标页面可操作”为准，不只依赖固定 sleep
- 允许保留少量 `waitForTimeout` 作为兜底，但必须从属于状态判定

## `patterns/instance-ops.md`

### 职责

定义实例域原子操作的统一描述格式，并先提供少量高频操作样板，
作为后续迁移模板。

### 本轮迁移策略

本轮优先重写以下 3 个高频操作:

- `create_instance`
- `delete_instance`
- `attach_volume`

其他实例操作先保留，但统一标记为“待迁移到新模板”，避免一次性
重写过大文件。

### 每个操作的统一模板

每个操作采用同一结构:

1. 用途
2. 参数
3. 前置条件
4. 执行步骤概览
5. 成功判定
6. 失败信号
7. 返回值约定
8. `browser_run_code_unsafe` 示例

### 参数约定

参数分为两类:

- 显式输入参数:本次操作必须由调用方提供或覆盖
- 环境默认参数:可从 `/tmp/easystack-env.json` 读取的默认值

文档中应明确哪些参数是必填，哪些参数可以回退到环境默认值。

### 返回值约定

所有原子操作统一建议返回类似结构:

```json
{
  "ok": true,
  "resource": "instance",
  "action": "create",
  "name": "vm-01",
  "status": "Active",
  "message": "instance created"
}
```

失败时保持相同结构，但:

- `ok` 为 `false`
- `status` 填写观察到的最终状态或 `unknown`
- `message` 填写关键失败信息

### 成功标准

操作完成必须包含显式验证，例如:

- 创建实例后在列表中确认实例出现并达到目标状态
- 删除实例后确认实例不再出现在当前列表，或状态进入回收站预期
- 挂载卷后确认卷状态从 `Available` 变为 `In use`

## `patterns/quick-reference.md`

### 职责

作为 patterns 层的能力索引表，而不是伪函数清单。

### 调整方向

- 去掉“仿佛已有真实函数实现”的表达方式
- 改成“操作名 + 所在文档 + 参数摘要 + 返回值摘要 + 迁移状态”
- 明确哪些操作已经符合新契约，哪些仍是旧格式待迁移

### 推荐字段

索引表至少包含:

- 操作名
- 资源域
- 文档位置
- 必填参数
- 默认参数来源
- 返回结果
- 当前状态

其中“当前状态”用于区分:

- `ready`:已按新模板整理
- `legacy`:仍为旧格式
- `planned`:已计划但未迁移

## 迁移顺序

本轮执行顺序固定为:

1. 重写 `patterns/login.md`
2. 重构 `patterns/instance-ops.md` 的文档骨架
3. 将 `create_instance`、`delete_instance`、`attach_volume`
   迁移为新模板
4. 重写 `patterns/quick-reference.md`
5. 在 `instance-ops.md` 中标注未迁移操作

这样可以先收敛公共契约，再产出一个实例域样板，最后让索引层和
实现层对齐。

## 风险与控制

### 风险 1:一次性重写过大

`instance-ops.md` 体量较大，若试图一次迁移全部操作，容易造成文档
结构再次失控。

控制方式:

- 只迁移 3 个高频操作
- 其余操作保留并显式标记待迁移

### 风险 2:文档与真实平台版本不完全一致

部分 URL、按钮文案、页面布局可能受平台版本影响。

控制方式:

- 本轮只统一契约，不声称已完成真实环境验证
- 保留选择器和流程说明时，优先写成“判定逻辑”而非绝对实现细节

### 风险 3:历史文档仍残留旧口径

即使本轮完成后，`volume-ops`、`network-ops` 仍会保留旧风格。

控制方式:

- 在 `quick-reference` 中明确迁移状态
- 后续按同一模板逐步迁移其他资源域

## 验证方式

本轮不运行真实 UI 自动化，只做文档层定向验证。

完成后应满足:

1. 三份目标文档不再混用 Python Playwright 模板和 MCP Playwright
   JS 约定
2. 三份目标文档不再包含真实凭证硬编码
3. `quick-reference.md` 的索引能和 `login.md`、
   `instance-ops.md` 的内容对齐
4. `instance-ops.md` 中已迁移和未迁移的边界清晰

## 后续演进

如果本轮样板有效，下一轮可按相同模板迁移:

- `patterns/volume-ops.md`
- `patterns/network-ops.md`

再之后才考虑同步收敛:

- `connection.md`

## 本轮范围外但已识别的问题

以下问题已确认存在，但不纳入本轮实现范围，后续应单独建模或并入
下一轮 spec:

### 1. 基础约定层仍与 patterns 层存在冲突

涉及文件:

- `connection.md`
- `navigation.md`
- `SKILL.md`

问题概要:

- 仍残留 Python Playwright 模板
- 基础导航和 URL 口径未完全统一
- skill 顶层说明与实际执行文档存在局部脱节

建议后续目标:

- 将基础约定层统一收敛到 MCP Playwright 语义
- 统一登录、导航、等待、页面判定的全局口径
- 让 `SKILL.md` 的索引说明与下层文档严格对齐

### 2. 大体量资源知识文档可维护性偏弱

涉及文件类型:

- `instance/*.md`
- `volume/*.md`
- `network/*.md`
- `image/image.md`

问题概要:

- 单文件体量偏大
- 页面说明、操作步骤、校验点混在一起
- 高频路径与低频细节没有明显分层

建议后续目标:

- 按“页面结构 / 关键操作 / 校验点 / 常见坑”拆分
- 为每个资源域补充最小操作清单
- 将低频细节下沉到附录或专题文档

### 3. 资源路径与页面入口口径需要全局校验

问题概要:

- 部分文档同时出现 `/ens/*`、`/neutron/*`、`/glance/*`、
  `/container-registry/*` 等路径体系
- 当前无法仅凭文档判断哪些是版本差异，哪些是历史残留

建议后续目标:

- 建立页面路径对照表
- 标记版本差异或产品线差异
- 避免同一资源在不同文档中出现未解释的入口冲突

### 4. 凭证与环境样例需要进一步去敏感化

问题概要:

- 本轮只会清理目标文档中的硬编码
- 仓库其他文档仍可能保留真实地址、账号或密码样例

建议后续目标:

- 对整个 `easystack-ui-test` 目录做一次去敏感化清理
- 将所有样例统一替换为占位值或 env 配置引用
- 明确“示例值”和“真实环境值”不能混写

## 预期产出

本轮产出应是一个更稳定的 patterns 层样板:

- 公共前置能力口径统一
- 实例域至少 3 个高频操作完成模板化
- 索引层能准确表达当前能力和迁移状态
- 后续 volume / network 可以直接复用该模板推进
