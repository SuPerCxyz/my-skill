# Problem Analysis Report Format

问题分析完成后使用本格式输出结论。目标是让用户直接复制完整报告, 避免编辑器把
标题、列表、命令、日志或配置误识别为特殊行。

## Output Contract 输出约束

- 禁止在问题分析结论中使用 Markdown 表格。
- 结论标题和章节名使用普通文本, 列表使用数字项。
- 结论中的任何一行都不得以 `-`、`#` 或 `$` 开头, fenced code block 内同样适用。
- 命令不带 `$` shell prompt。原始日志或配置行命中禁用前缀时, 在原文前增加
  `原文: `, 不删除或改写原始内容。
- 命令使用 `bash` fenced code block; 日志使用 `text`; 配置使用对应语言标识。
- 标题后必须先输出 `一句话总结`, 用一个完整句子概括问题、原因和当前状态。
- 第 1 至第 4 节为必选章节, 不得省略。
- 第 5 至第 8 节为可选章节, 仅在有实际内容或确有必要时输出。
- 可选章节不适用时直接省略, 不要输出空标题或用 `无` 占位。
- 区分已确认事实、推断和待确认项; 没有充分证据时不得写成确定根因。
- 只保留支持结论的关键日志, 不粘贴大段无关输出。
- 密钥、密码、token 和其他凭据必须脱敏。

## Required Structure 必选结构

以下模板定义第 1 至第 4 节。尖括号内容应替换为实际信息, 不要原样输出。

````text
问题分析结论

一句话总结: <用一句完整的话概括故障现象、已确认或最可能原因以及当前状态>

1. 问题概述

问题现象:
<用户看到的错误或异常>

影响对象:
<受影响的资源、服务、节点或业务>

当前状态:
<持续异常、间歇性异常、已恢复或待确认>

2. 根因结论

直接原因:
<直接触发故障的原因>

根本原因:
<更深层的配置、代码、资源或环境原因>

结论状态:
<已确认、高概率、初步判断或暂无法确认>

判断依据:
<说明证据如何支持结论>

3. 关键证据

证据 1

来源: <pod、服务、节点、日志文件或命令>
时间: <日志时间或检查时间>
对象: <UUID、pod 名称或其他关联对象>

```text
<关键日志、状态或错误信息>
```

证据 2

<仅在存在第二组关键证据时输出, 格式同上>

4. 排查过程

步骤 1

检查内容: <检查了什么>

检查结果: <发现了什么>

阶段结论: <该结果说明什么>

步骤 2

<按实际排查步骤继续, 不需要补足固定数量>
````

## Optional Structure 可选结构

第 5 至第 8 节按问题实际情况选择。需要输出时保持以下顺序; 不需要时省略整节。

````text
5. 影响分析

已确认受影响:

对象 1: <受影响对象>

已确认不受影响:

对象 1: <不受影响对象>

潜在影响:

对象 1: <尚未完全确认的影响>

6. 处理建议

立即处理:

1. <当前建议执行的操作>
2. <后续操作>

长期改进:

1. <配置、代码、监控或流程改进建议>

7. 验证方式

验证步骤 1

验证目标: <需要确认什么>

```bash
<验证命令>
```

预期结果:
<正常情况下应看到什么>

实际结果:
<已经执行时填写实际结果; 未执行时明确写 `未执行`>

8. 未确认项与限制

未确认项:

事项 1: <仍需确认的信息>

排查限制:

限制 1: <权限、日志缺失、时间范围或环境访问限制>

下一步:

下一步 1: <继续排查所需的最小动作>
````

## Selection Rules 章节选择规则

- 只有需要明确故障边界时才输出第 5 节。
- 只有用户需要修复、缓解或长期改进方案时才输出第 6 节。
- 只有存在可执行验证动作或需要记录验证结果时才输出第 7 节。
- 只有结论仍有不确定性、排查受限或需要继续调查时才输出第 8 节。
- `一句话总结` 始终必选, 必须是一个完整句子, 不拆成列表或多行字段。
- 简单问题也必须保留第 1 至第 4 节, 但每节可以简洁表达。
- 同一证据不要在 `关键证据` 和 `排查过程` 中重复粘贴; 排查过程只描述结果和含义。
- 输出前逐行检查禁用前缀; 发现行首为 `-`、`#` 或 `$` 时改用数字项、普通文本
  章节名、裸命令或 `原文: ` 前缀。
