# Problem Investigation Report Format

问题调查完成后使用本格式输出报告。调查开始前先读取本格式, 按时间线事件字段规划
最小证据链。发现关键操作、状态变化、直接失败或底层触发机制时, 立即保留可直接引用的
原始日志或其他直接证据、来源、时间、关联标识和必要上下文。默认报告包含核心结论、带直接证据的关键
操作时间线以及未确认项与限制, 让阅读者理解问题如何发生、造成什么影响以及应如何处理。
完整日志上下文和深入判断仅在用户明确要求时输出。

## Output Contract 输出约束

- 禁止在问题调查报告中使用 Markdown 表格。
- 报告标题固定为 `问题调查报告`, 章节名使用普通文本, 列表使用数字项。
- 只有第 1 至第 4 节的章节号允许使用与列首对齐的裸数字序号 (`1.` 至 `4.`)。
- 章节内子项禁止使用与章节号同列并从 1 重新开始的裸数字序号 (`1.`、`2.`),
  必须使用带前缀标签的计数项 (`对象 1:`、`处理 1:`、`证据 1`、`步骤 1`),
  否则编辑器会把章节号和子项合并成连续有序列表并自动重新编号。
- 报告中的任何一行都不得以 `-`、`#` 或 `$` 开头, fenced code block 内同样适用。
- 命令不带 `$` shell prompt。原始日志或配置行命中禁用前缀时, 在原文前增加
  `原文: `, 不删除或改写原始内容。
- 命令使用 `bash` fenced code block; 日志使用 `text`; 配置使用对应语言标识。
- 标题后直接输出一段原因概述, 不添加 `一句话总结`、`摘要` 或其他字段标签。
  原因概述应在一个自然段内写清故障对象、关键触发操作、问题原因和最终结果。
- `通俗说明`位于`问题原因`前, 使用一个自然段向不了解上下文的读者解释已经验证的
  故障机制和结果。它只转述证据支持的事实, 不重复时间线、原始日志或引入新判断。
- 资源不得只写 UUID。首次出现时使用 `显示名称 (完整 UUID)`, 同一章节后续可使用
  `显示名称 (UUID 前 8 位)`。无法取得显示名称时明确写 `显示名称未查到 (完整 UUID)`。
- 计算资源统一使用 `云主机` 描述, 禁止使用 `虚拟机`、`实例`、`VM`、`server` 等
  替代描述。
- OpenStack 侧逻辑卷统一使用 `云硬盘` 描述, 禁止使用 `云盘`、`卷` 等替代描述。
- `云硬盘` 挂载到云主机或节点后, 逻辑资源仍称 `云硬盘`, 节点上呈现的具体设备称
  `块设备` 并附设备名, 如 `云硬盘 xxx 挂载后对应块设备 /dev/sdb (dm-2)`。
- 日志、命令和配置原文中的技术标识 (如 `instance-<HEX>`、`volume-<id>`、`VM UUID`)
  保持原样, 不改写。
- 第 1 至第 3 节为必选章节。默认不输出第 4 节, 报告末尾提示用户可按需继续输出
  详细分析; 只有用户明确需要时才输出第 4 节。
- 可选章节不适用时直接省略, 不要输出空标题或用 `无` 占位。
- 不设置 `结论状态`、`当前状态` 或 `后续影响` 固定字段。用户明确要求相应信息时,
  再基于实际证据补充。
- 事实和原因必须由本次实际查询、日志核对、目标环境验证或受控测试直接支持。
- 结论只适用于已验证的环境、版本、配置、组件、对象和时间窗, 不得外推到
  未验证条件。
- `未查到异常` 和 `未执行测试` 不能证明问题不存在。
- 不输出未经验证的推测、经验性判断和假设。`未确认项与限制` 只记录
  客观验证缺口和所需的最小验证。
- 时间线每个事件必须有至少一种直接证据, 优先保留支持该事件的具体日志原文, 但不粘贴
  大段无关输出。没有日志时可以使用实际命令输出、数据库记录或配置, 并明确说明日志缺口。
- 结论必须区分用户现象、直接失败和底层根因。超时、状态异常、上游错误和单一错误栈
  只能作为线索或直接失败, 不得在未验证触发机制时写成根因。
- 根因必须由关联组件、request ID 或资源标识、配置、运行逻辑或外部依赖的实际证据
  说明其如何导致直接失败。只能确认直接失败时, 明确写`直接失败已确认, 根本原因未确认`,
  并在第 3 节记录最小补证动作。
- 调研 kernel 或系统软件包时, 可以引用本地临时目录中的社区源码, 但必须同时写明
  仓库、发行版或上游版本、完整 commit、补丁状态和源码路径。源码版本未与目标环境
  精确对齐时, 只能作为辅助线索或未确认项, 不得单独写成根因。
- 密钥、密码、token 和其他凭据必须脱敏。

## Required Structure 必选结构

以下模板定义默认输出的第 1 至第 3 节。尖括号内容应替换为实际信息, 不要原样输出。

`问题原因`是报告主体, 必须详细写明故障发生过程和已验证的底层触发机制:

- 按故障实际发生顺序组织, 每个因果阶段另起一段。
- 每段以具体时间点或时间范围开头, 优先使用 `YYYY-MM-DD HH:MM:SS`。只有日期时
  使用 `YYYY-MM-DD`; 无法从证据确认时间时写 `时间待确认`, 不得编造时间。
- 每段写清发生了什么操作、涉及哪个带显示名称和 UUID 的资源、由哪个节点或组件
  处理、产生什么状态变化或错误, 以及该结果如何引出下一阶段。
- 最后一段明确故障最终如何落到用户看到的现象, 避免只列错误而不连接因果关系。
- 明确区分用户现象、直接失败和底层根因。只有能够说明直接失败为何发生的组件、配置、
  运行逻辑或外部条件才是根因; 证据不足时只说明直接失败和证据缺口。
- 具体日志原文或其他直接证据放在第 2 节对应的时间线事件中, `问题原因`只解释证据所证明
  的事件和因果关系。

````text
问题调查报告

<使用一个自然段说明故障对象、关键触发操作、问题原因和最终结果, 不加摘要标签>

1. 核心结论

问题现象:
<用户看到的错误或异常>

通俗说明:
<用一个自然段向不了解上下文的读者解释已经验证的故障机制和最终结果, 不加入未验证推断>

问题原因:

<YYYY-MM-DD HH:MM:SS 或时间范围>, <操作、带显示名称和 UUID 的资源、节点或组件、
状态变化或错误, 以及该结果如何引出下一阶段>。

<下一个具体时间点或时间范围>, <继续说明下一阶段的操作、资源、处理组件、结果和
因果关系>。

<最终时间点或时间范围>, <说明前序残留或异常如何影响目标操作并形成用户看到的
故障>。

问题影响:
<说明本次已经造成的资源、服务或业务影响, 以及证据能够支持的风险边界>

修复建议:
<使用一句稍微丰富且可执行的话, 写清处理对象、建议动作和预期结果, 不展开成长清单>

2. 关键操作时间线与证据

事件 1

时间: <操作发生时间或时间范围>
操作: <挂载、卸载、retype、迁移、重启、配置变更等实际操作>
资源: <显示名称 (完整 UUID); 多个资源使用分号分隔>
节点或组件: <实际执行或处理操作的节点、pod、服务或组件>
结果: <状态变化、返回结果或错误>
证据来源: <日志文件、pod、服务、节点、命令、数据库或配置; 离线日志增加 file:line>

```text
<直接证明该时间点操作和结果的日志原文或其他直接证据及必要上下文>
```

证据说明:
<说明证据证明了什么, 以及该事件如何引出下一个时间线事件; 没有日志时明确写未取得对应日志>

事件 2

<按时间顺序继续。每个事件都必须包含直接证据和证据说明, 不记录无关排查命令>

3. 未确认项与限制

未确认项:

事项 1: <仍需确认的信息; 没有时说明当前证据范围内未发现影响结论的未确认项>

排查限制:

限制 1: <权限、日志缺失、时间范围或环境访问限制; 没有时说明当前调查无已知限制>

下一步:

下一步 1: <继续确认未确认项或消除限制所需的最小动作; 无需继续时明确说明>

如需查看关键操作时间线中每个事件的完整日志上下文和深入判断, 可以继续输出详细分析。
````

## Optional Structure 可选结构

第 4 节仅在用户明确要求完整日志上下文、排查过程、审计材料或复核结论时输出。

````text
4. 详细分析

事件 1: <与第 2 节事件 1 使用相同的事件名称>

时间: <与第 2 节事件 1 相同的时间或时间范围>
操作: <与第 2 节事件 1 相同的操作>
资源: <显示名称 (完整 UUID)>
节点或组件: <处理该事件的节点、pod、服务或组件>
证据来源: <与第 2 节一致, 离线日志增加更完整的 file:line 范围>

```text
<在第 2 节直接证据基础上补充该时间点的完整证据上下文和关联服务日志>
```

详细说明:
<解释日志记录的状态变化、错误及其与前后事件的因果关系>

事件 2: <与第 2 节事件 2 对应>

<按第 2 节事件顺序逐点继续, 不得遗漏时间线事件。补充完整上下文日志和深入判断;
确实没有更多日志时, 明确写出日志缺口, 不得编造日志>
````

## Selection Rules 章节选择规则

- 第 1 至第 3 节必选且不得省略, 章节号必须连续。第 1 节详细解释核心结论,
  第 2 节按时间顺序合并关键操作和对应证据, 第 3 节如实记录未确认项、排查限制
  和下一步。
- 第 1 节必须依次包含`问题现象`、`通俗说明`、`问题原因`、`问题影响`和`修复建议`, 缺一不可。
- `通俗说明`只概括已经验证的故障机制和结果, 方便不了解上下文的读者理解, 不得替代
  `问题原因`中的时间顺序、因果关系和证据边界。
- `问题影响`只写已发生影响和证据支持的风险边界, 不扩展未经验证的未来影响。
- `修复建议`只写一句稍微丰富且可执行的话, 包含处理对象、建议动作和预期结果,
  不拆成立即处理、长期改进或多项清单。
- 第 2 节每个事件必须包含时间、操作、资源、节点或组件、结果、证据来源、直接证据
  和证据说明, 不得把时间线与证据拆成两个章节。优先使用日志; 没有日志时明确写
  `未取得对应日志`, 提供实际命令输出、数据库记录或配置等替代证据, 并将日志缺口同步
  写入第 3 节, 不得编造日志。
- 第 4 节默认不输出。只有用户明确要求完整证据链、排查过程、审计材料、复核结论,
  或对当前判断提出争议时才输出。
- 默认报告第 3 节后固定提示用户可继续输出详细分析, 但不提前展开第 4 节内容。
- 输出第 4 节时, 必须与第 2 节关键操作时间线逐点对应: 事件编号、顺序、时间、操作
  和资源保持一致, 每个事件补充完整证据上下文、关联服务日志和深入判断, 不得遗漏。
- 某个时间线事件没有对应日志时, 使用实际数据库记录、配置或命令输出作为证据并
  明确说明日志缺口, 不得伪造日志来补齐格式。
- 开头原因概述和第 1 节必须逐项反查证据。无法指向实际日志、命令、配置或测试
  结果的内容必须删除或放入第 3 节, 不得写成已确认原因。
- `问题原因`必须按时间顺序详细展开。每个因果阶段以具体时间点、时间范围或
  `时间待确认`开头, 不得使用`随后`、`之后`等词代替段首时间。
- `问题原因`不得把用户现象、超时、状态异常、上游错误或单一错误栈直接写成根因。
  必须继续说明已验证的触发机制及其如何导致直接失败; 无法验证时明确根本原因未确认,
  并将最小补证动作写入第 3 节。
- 第 1 节解释因果关系, 第 2 节合并操作事实与对应日志, 两者不重复粘贴相同段落。
- 输出前逐行检查禁用前缀; 发现行首为 `-`、`#` 或 `$` 时改用数字项、普通文本
  章节名、裸命令或 `原文: ` 前缀。
- 输出前检查章节完整性和序号: 第 1 至第 3 节必须存在并连续递增; 输出详细分析时
  只能作为第 4 节, 禁止章节跳号。
- 输出前检查序号冲突: 任何行首裸数字序号只能出现在第 1 至第 4 节章节号位置,
  子项一律使用 `对象 1:`、`处理 1:`、`改进 1:`、`事项 1:`、`限制 1:`、
  `下一步 1:`、`证据 1`、`步骤 1` 等带标签的计数项, 不得重新从 1 裸编号。
